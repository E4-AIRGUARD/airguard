# 연기 팬 제어 + 온도 팬 제어 통합 가이드

> 이 문서는 전달본 참고 자료입니다. 현재 통합 실행은 상위 `../INTEGRATION.md`와 `../../README.md`를 따릅니다. 통합 PM 사건은 `../pm_recovery.py`에서 실제 DATA 시각·PWM/RPM·온습도로 기록합니다. 아래 `SmokeFan(event_db=...)` 경로는 PM 단독 요구값을 기록하며 실측 팬 피드백으로 해석하지 않습니다. 로컬 보완으로 센서 공백·비유한 값·중복 시각 처리와 Windows 업로더 잠금을 추가했습니다. 선택 category ALTER는 `schema.sql`에서 주석 처리했습니다.

## 파일
| 파일 | 역할 |
|---|---|
| `smoke_fan.py` | 연기 제어를 함수 하나(`SmokeFan.step(pm)`)로 감싼 통합용 모듈. 센서·팬을 직접 만지지 않음 |
| `integration_example.py` | 연기 + 온도를 한 루프에서 합치는 예제 (`--fake`로 센서 없이 실행 가능) |
| `fan_controller.py`, `model.json` | 제어기 본체와 161행 회귀 모델 (수정 불필요) |
| `run_on_jetson.py` | 연기 제어만 단독으로 돌릴 때 (기존) |

## 연결 방법
1. 메인 루프에서 1초마다 `cmd = smoke.step(pm)` 호출. `pm`은 PM2.5 원시값이고 센서 오류면 `None`.
2. `cmd.intake`, `cmd.exhaust`는 연기 쪽이 요구하는 PWM(%)이며 35/60/100 중 하나.
3. 온도 쪽도 같은 형태 (흡기%, 배기%)로 요구값을 내면 `combine_max`로 합쳐서 `set_fan`에 한 번만 출력.

## 합치는 규칙 (제안, 팀 합의 필요)
- 흡기·배기 각각 두 요구 중 더 큰 값을 사용. 한쪽이 환기를 요구하는데 다른 쪽이 약하게 낮추는 일을 막기 위함.
- 연기 쪽은 평소(범위 안) 35/35를 요구하므로, 온도가 요구가 없을 때는 `(35, 35)`를 넘기면 됨.
- 단점: 둘 다 동시에 켜지면 에너지 절감 효과가 줄어듦. 온도 쪽 선택 규칙을 몰라서 이 부분은 합의가 필요함.

## 알아둘 점
- 연기 쪽 판단 주기 1초, 조합을 바꾼 뒤 최소 25초 유지(급상승·측정 상한 초과로 세게 올릴 때만 예외). 합칠 때 온도 쪽이 자주 바뀌면 출력은 합쳐진 값이라 더 자주 바뀔 수 있음.
- 센서 값이 10초 넘게 안 들어오면 연기 쪽이 100/100을 요구 (`sensor_invalid_or_stale`).
- 기본값: 마감 70초(PM이 500 아래로 내려온 뒤 PM50까지), 범위 PM50 이하는 35/35. `SmokeFan(deadline_s=..., range_pm=...)`으로 바꿈.
- 에너지는 RPM 기반 추정이고, 온도 쪽 식((in/100)^3 + (out/100)^3 x 시간)과 가정이 달라 숫자를 바로 더하면 안 됨. 같은 식으로 맞춰 비교해야 함.
- 이 통합 루프는 센서·팬 실물로 시험하지 않았고, 가짜 PM으로 호출이 되는 것만 확인함.

## 이벤트 DB 저장 (PM 50 초과 -> 50 이하 회복)
팀 DB 문서(airguard `7_DB구조_조회방식`)의 `e4_recovery_events`, `e4_recovery_samples` 형식에 맞춰 만들었다.
| 파일 | 역할 |
|---|---|
| `event_recorder.py` | PM이 50을 넘으면 이벤트 시작, 50 이하를 3초 유지하면 회복 확정(status=completed, recovery_seconds = 회복 확정 - 시작). 중간 샘플(PM, 적용 PWM)을 같이 기록. 종료·비정상 종료는 interrupted |
| `uploader.py` | 로컬 대기열(`pending.sqlite3`)을 MySQL로 UPSERT. commit 성공 뒤에만 로컬 삭제, 실패하면 큐 유지 |
| `schema.sql` | 이벤트·샘플 테이블 정의 (팀 문서 사본) |

사용
- 단독: `python3 run_on_jetson.py --live --event-db pending.sqlite3 --device-id jetson-1`
- 통합 모듈: `SmokeFan(event_db='pending.sqlite3', device_id='jetson-1')`
- 업로드: `DB_HOST DB_PORT DB_USER DB_PASSWORD DB_NAME DB_CA` 환경변수를 설정하고 `python3 uploader.py pending.sqlite3` (pymysql 필요). 접속 정보는 코드·저장소에 넣지 말 것.

주의
- 온도·습도·가스·RPM 열은 이 프로그램이 읽지 않아 NULL이고 `valid_json`에 pm25만 true로 표시된다. 온도 쪽 코드가 같은 이벤트 기록기를 쓰면 이 열들은 그쪽에서 채워야 하고, 이벤트 기준이 온도(26도)와 연기(PM50)로 따로 있어 한 이벤트로 합칠지 정해야 한다.
- 회복 기준은 `PM <= 50`(문서의 온도는 `<` 기준). 필요하면 `event_recorder.py` 비교식을 바꾼다.
- 가짜 PM으로 이벤트 생성·샘플 기록·회복 확정과 업로더 SQL 생성(가짜 연결)만 확인했다. 실제 Aiven 접속·업로드는 시험하지 않았다. 운영 스키마와 같은지 `SHOW CREATE TABLE`로 확인 필요.

### 카테고리 (연기 / 온도)
- 이벤트에 `category`를 저장: 연기 `pm25`, 온도 `temperature` (`EventRecorder(..., category=...)`, 기본 `pm25`). 온도 쪽도 같은 기록기를 쓰면 `category='temperature'`로 만들면 된다.
- 지금 DB 구조 그대로면 `config_json`의 `category`에 들어가서 `JSON_UNQUOTE(JSON_EXTRACT(config_json,'$.category'))`로 거를 수 있다.
- 거르기 편하게 열을 따로 두려면 `schema.sql` 하단의 ALTER TABLE을 DB 담당이 실행하고, 업로더에 `E4_CATEGORY_COLUMN=1`을 설정한다(열을 만들기 전에 켜면 업로드가 실패함).
